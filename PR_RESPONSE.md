# PR Responses

- **mjgarton** - concern that the catch-all arm in `extract_dml_filters` could miss future predicate-bearing nodes and silently drop filters (risking full-table deletes).
  - The DML input we build for DELETE/UPDATE currently only carries predicates in `Filter` nodes or in `TableScan.filters` after pushdown, so the match over those two variants is exhaustive for today's plan shapes; anything else in the tree would be projections/joins introduced by the planner that do not store filters. The regression tests for pushdown paths--`test_delete_filter_pushdown_extracts_table_scan_filters` and `test_delete_compound_filters_with_pushdown`--in [datafusion/core/tests/custom_sources_cases/dml_planning.rs#L273-L336](datafusion/core/tests/custom_sources_cases/dml_planning.rs#L273-L336) should catch any future optimizer change that relocates predicates away from these nodes. If we ever add a new logical node that can hold filters, I'll extend `extract_dml_filters` instead of relying on the default case.
